# HANSALEHLAK V8 — FRONTEND MASTER ENGINEERING SPECIFICATION

**الحالة:** المرجع التنفيذي المعتمد للمرحلة الحالية — Frontend Only  
**الإصدار:** 2.0  
**تاريخ التحديث:** 8 نوفمبر 2026  
**النطاق:** واجهات المستخدم، تجربة الاستخدام، بنية JavaScript/CSS/HTML، الأصول، التفاعلات، البيانات التجريبية، والاختبارات الأمامية.

> هذه الوثيقة تحكم العمل الحالي. أي وثيقة أقدم تتناول Backend أو Database أو API أو صلاحيات خادمية لا تُعد تكليفًا تنفيذيًا في المرحلة الحالية. لا تحذف الملفات أو الواجهات المستقبلية لمجرد أنها Placeholder؛ المطلوب توثيق حالتها وحدودها بدقة.

## 1. الهدف ومبدأ التنفيذ

بناء تجربة Frontend متماسكة وقابلة للتطوير، بحيث يستطيع مهندس أو وكيل AI فهم الصفحة والملفات المرتبطة بها، تنفيذ تغيير محدود، والتحقق من عدم كسر بقية التطبيق. يجب أن يكون كل قرار قابلًا للتتبع إلى صفحة أو مكوّن أو نمط أو سلوك واضح.

**مبدأ حاكم:** لا تفترض وجود خدمة خلفية. استخدم البيانات المحلية/التجريبية الموجودة فقط، وميّز بوضوح بين السلوك المنفذ والمحاكاة والهيكل المستقبلي.

## 2. حدود النطاق

### داخل النطاق
- HTML structure, semantic markup, CSS architecture, JavaScript modules and current classic-script compatibility.
- Customer, Provider, Guest and Admin frontend shells/pages، سواء كانت منفذة أو مخططة.
- Design system, tokens, typography, RTL, responsive layouts, iconography, assets and motion.
- Navigation, local UI state, forms, validation, dialogs, tables, cards, filters, sorting, search and feedback states.
- Mock/local data behavior, localStorage/IndexedDB usage الحالي، وواجهات العرض التي تعتمد عليها.
- Accessibility, performance perceived by user, browser behavior, PWA presentation/offline UI, frontend tests and visual QA.
- File ownership, module boundaries, imports/script order, dependencies and frontend integration contracts.

### خارج النطاق حاليًا
- تصميم أو تنفيذ قواعد البيانات أو migrations أو database security rules.
- إنشاء Backend أو APIs إنتاجية أو Cloud Functions أو Workers.
- تكامل مصادقة حقيقي أو RBAC خادمي أو جلسات إنتاجية.
- بوابات دفع حقيقية، إرسال رسائل/إشعارات خارجية، أو تكاملات طرف ثالث حقيقية.
- قرارات النشر والبنية السحابية والتشغيل الخلفي.

يجوز ذكر نقاط التكامل المستقبلية كحدود واجهة فقط، دون تنفيذها أو جعلها شرطًا لإنجاز مهمة Frontend.

## 3. وصف النسخة التي تم فحصها وحدودها

- تطبيق العميل هو أكثر أجزاء الواجهة اكتمالًا، ويضم صفحات/منطقًا حقيقيًا يعمل محليًا.
- بيانات السوق والكتالوج الحالية تجريبية ومحلية؛ لا تُعرض على أنها بيانات إنتاجية.
- المرفقات الحالية تستخدم تخزينًا محليًا عبر IndexedDB.
- مساحة مقدم الخدمة الحالية مرتبطة بجسر توافق/Runtime قديم؛ ملفات الصفحات المستقلة لا تعني أن الفصل قد اكتمل.
- تطبيق الإدارة المستقل يحتوي على هيكل وملفات مستقبلية/Placeholder؛ لا تفترض وجود لوحة إدارة مكتملة.
- بعض ملفات `services/` حدود مستقبلية أو وحدات محلية وليست APIs حقيقية. افحص محتوى الملف قبل استخدامه.
- ملفات `shared/` قد تحتوي تنفيذًا فعليًا أو حدود فصل مستقبلية؛ حالة كل ملف في `AI_PROJECT_MAP` هي نقطة البداية، وليست بديلًا عن فحص الكود.

## 4. التطبيقات والأدوار على مستوى الواجهة

| التطبيق | المستخدم | الهدف البصري/الوظيفي | الحقيقة الحالية |
|---|---|---|---|
| `apps/customer` | العميل | اكتشاف الخدمات، إنشاء طلب، متابعة السوق والطلبات، الحساب والدعم | الأكثر اكتمالًا؛ أجزاء من العرض لا تزال مجمعة في وحدات قائمة |
| `apps/provider` | مقدم الخدمة | لوحة العمل، الطلبات، العروض، المواعيد، الأرباح والملف | Runtime تجريبي مختلط؛ الاستقلالية غير مكتملة |
| `apps/admin` | فريق الإدارة | إدارة وتشغيل المنصة عبر وحدات ولوحات | غالبية الملفات هياكل مستقبلية وليست واجهات مكتملة |
| `apps/guest` | الزائر | سياسة الدخول العام ونقطة بدء تجربة الزائر | حدود/هيكل مستقبلي بحسب حالة الملف |

لا تُنفذ مصادقة حقيقية في هذه المرحلة. إذا احتاجت الواجهة حالة مستخدم للاختبار، استخدم Fixture أو Demo State معلنة بوضوح ولا تصفها كتحقق أمني.

## 5. معايير تعريف حالة التنفيذ

- **IMPLEMENTED:** يوجد كود فعلي يؤدي المسؤولية الموصوفة. يلزم اختباره في سياقه قبل التعديل.
- **PARTIALLY IMPLEMENTED:** يوجد تنفيذ، لكن جزءًا من السلوك أو الفصل أو الربط ناقص.
- **LEGACY:** تنفيذ قديم يعتمد عليه مسار قائم؛ لا يحذف قبل تحديد البديل وإثبات التكافؤ.
- **PLACEHOLDER:** ملف/حد معماري أو تعليق/هيكل لا يحقق تجربة كاملة. لا يُعامل كميزة منفذة.
- **CONFIGURATION/DOCUMENTATION:** إعداد أو توثيق أو أصل، وليس صفحة وظيفية.

كل مهمة يجب أن تسجل: الحالة قبل التعديل، التغيير المنفذ، الملفات المتأثرة، السلوك الذي تم التحقق منه، وما بقي.

## 6. معمارية Frontend المعتمدة

### 6.1 طبقات المسؤولية
1. **App entry / Shell:** بدء التطبيق، تحميل الاعتمادات، إعداد الحاوية العامة، وإدارة دورة العرض.
2. **Router / Navigation:** تحديد الصفحة الحالية، التنقل، التعامل مع الرجوع/التحديث والروابط المباشرة عندما تكون مدعومة.
3. **Page modules:** تركيب واجهة صفحة واحدة وربط أحداثها بمنطق العرض. الصفحة لا تصبح مخزن بيانات شاملًا.
4. **Feature logic:** قواعد الواجهة الخاصة بالميزة مثل wizard/search/filters.
5. **Shared UI components:** عناصر قابلة لإعادة الاستخدام مع API واضح ومتسق.
6. **Design system:** tokens, typography, layout primitives, component styles and responsive rules.
7. **Local data adapters:** مصادر البيانات التجريبية/المحلية الحالية. لا تسمَّ API إذا لم تكن تتصل بخدمة فعلية.
8. **Utilities:** تنسيق التاريخ/العملة، التحقق، sanitization، ورسائل الخطأ. لا تنشئ نسخًا مكررة من وظيفة موجودة.

### 6.2 قواعد الاعتماد
- الصفحة تعتمد على مكونات مشتركة وأدوات وخدمات محلية؛ لا تجعل المكونات العامة تعتمد على صفحة بعينها.
- `shared/` لا يستورد من `apps/`.
- التطبيق لا يستورد من تطبيق آخر مباشرة؛ انقل المشترك إلى `shared/` بعد إثبات الحاجة.
- لا تنشئ اعتمادًا دائريًا.
- تجنب إضافة framework أو bundler أو مكتبة جديدة دون مبرر موثق وموافقة صاحب المشروع.
- حافظ على ترتيب تحميل السكربتات الحالي في HTML حتى يتم ترحيله صراحةً إلى imports آمنة ومختبرة.
- لا تعِد تسمية global أو function أو DOM hook مستخدم في أكثر من ملف قبل فحص كل المراجع.

### 6.3 قواعد ملكية الملفات
كل ملف له مسؤولية أساسية واحدة. عند الحاجة لتعديل ملف مشترك، يجب توضيح أثره على كل التطبيقات المستهلكة له. لا تنشئ ملفًا جديدًا لمجرد نقل بضعة أسطر؛ أنشئه عندما يحقق حدًا معماريًا واضحًا وقابلًا للاختبار.

## 7. عقد الصفحة (Page Contract) — إلزامي لكل صفحة

يجب أن يحتوي توثيق كل صفحة على:
1. الاسم والمسار والـ app/role المستهدف.
2. الغرض الأساسي والهدف الذي يجب أن ينجزه المستخدم.
3. نقطة الدخول وطريقة الوصول والتنقل للخارج.
4. هيكل الصفحة من أعلى لأسفل: header, navigation, content sections, footer/overlays.
5. المكونات المستخدمة ومصدر كل مكون.
6. البيانات المعروضة وشكل Fixture المطلوب ومصدرها المحلي الحالي.
7. التفاعلات: trigger → state change → visible result.
8. حالات الصفحة: initial, loading, populated, empty, error, success, disabled, offline عند انطباقها.
9. قواعد الحقول والتحقق ورسائل الخطأ.
10. responsive behavior عند mobile/tablet/desktop، بما في ذلك ترتيب العناصر والإخفاء/التحويل.
11. RTL, keyboard and screen-reader expectations.
12. الملفات المالكة للصفحة والملفات التي تعتمد عليها.
13. حدود التنفيذ الحالي وما لا يعمل بعد.
14. Acceptance criteria قابلة للفحص يدويًا أو آليًا.

لا تكتب وصفًا عامًا مثل «تعرض بيانات الطلبات». حدد الأعمدة/البطاقات، الترتيب، حالات عدم وجود نتائج، والفعل الناتج عن كل زر. إذا لم يتم فحص التفاصيل الفعلية، اكتب **غير متحقق — يحتاج فحصًا** بدل التخمين.

## 8. عقد المكوّن (Component Contract)

لكل مكون مشترك وثّق: الاسم، الملف، الغرض، أماكن الاستخدام، مدخلات/خيارات الإنشاء، DOM الناتج، classes/data attributes، الأحداث، الحالات المرئية، سلوك لوحة المفاتيح، responsive behavior، إدارة التركيز، وما لا يجب أن يفعله.

- المكوّن يعرض واجهة ولا يمتلك تدفق أعمال صفحة كاملة.
- لا تضع نصوصًا أو ألوانًا أو مسافات متكررة بشكل عشوائي إذا كان لها token أو variant معتمد.
- أي عنصر يبدو قابلًا للنقر يجب أن ينفذ فعلًا أو يظهر disabled مع سبب مفهوم.
- استخدم عناصر HTML دلالية؛ لا تستبدل button بـ div قابل للنقر دون سبب قوي.

## 9. نظام التصميم والهوية البصرية

### 9.1 مصدر الحقيقة
ابدأ من `shared/design-system/design-system.css` وملفات الأنماط الحالية للتطبيقات. لا تفترض أن ملفات `tokens.css` أو `typography.css` المستقبلية تحتوي تنفيذًا لمجرد وجودها.

### 9.2 توثيق كل token
لكل token يجب توضيح: الاسم، القيمة الحالية، الاستخدام، السياق، وما إذا كان عامًا أو خاصًا بتطبيق. لا تستحدث قيمًا متقاربة تؤدي إلى تشتت الهوية.

### 9.3 قواعد واجهة
- الحفاظ على هوية هنصلحلك وأصول الشعار المعتمدة.
- توحيد مستويات العناوين، أحجام النص، عرض المحتوى، المسافات، الحواف، الظلال، الحدود، وحالات التركيز.
- اعتماد RTL كمسار أساسي، لا كتصحيح لاحق.
- عدم استخدام اللون وحده لشرح الحالة؛ أضف نصًا/أيقونة.
- الحركة قصيرة وهادفة ولا تعطل القراءة أو التفاعل. احترم `prefers-reduced-motion`.
- الأيقونات من Registry المعتمد متى كان مناسبًا؛ لا تخلط مصادر وأوزانًا بصرية بلا سبب.

## 10. Responsive & Mobile-first

كل صفحة تختبر على الأقل عند عروض مرجعية: 360px، 390px، 768px، 1024px، 1440px. هذه نقاط اختبار وليست بالضرورة breakpoints مفروضة.

يجب توثيق: تغيّر الأعمدة، ترتيب العناصر، overflow، navigation pattern، أحجام أهداف اللمس، sticky/fixed elements، dialogs/sheets، الجداول، والنصوص الطويلة. ممنوع علاج overflow بإخفاء المحتوى المهم أو تعطيل التمرير دون بديل.

## 11. التفاعل والحالات

لكل تفاعل اكتب: **المحفز → الشروط → التغيير في الحالة → النتيجة المرئية → إمكانية التراجع/الإلغاء**.

حالات الواجهة القياسية: idle, hover, focus-visible, pressed, disabled, loading, success, warning, error, empty, offline. لا تعرض success قبل نجاح العملية المحلية الفعلية. لا تدّع أن إرسالًا خارجيًا أو حفظًا سحابيًا حدث إذا كانت العملية محاكاة.

## 12. النماذج والتحقق

- لكل حقل label واضح، وصف عند الحاجة، required state، format، min/max، ورسالة خطأ مرتبطة به.
- تحقق من الإدخال قبل تغيير الخطوة أو الحفظ المحلي.
- حافظ على القيم عند ظهور خطأ؛ لا تمسح النموذج دون قصد.
- حدد سلوك الإلغاء وإعادة الضبط والحفظ كمسودة.
- امنع double-submit على مستوى الواجهة عند وجود عملية async محلية.
- لا تعتبر تحقق المتصفح حماية أمنية؛ هو تحسين تجربة فقط.

## 13. البيانات التجريبية والحالة المحلية

- Fixtures واضحة ومنفصلة قدر الإمكان عن render functions.
- استخدم بيانات عربية واقعية ومتنوعة، مع حالات طويلة/ناقصة/فارغة وحدود قصوى لاختبار التصميم.
- وضّح مصدر كل بيانات: static fixture, localStorage, IndexedDB, in-memory.
- لا تستخدم بيانات شخصية حقيقية.
- لا تخلط حالة واجهة مؤقتة مع بيانات دائمة.
- عند فشل التخزين المحلي، اعرض رسالة مفهومة واحتفظ بما يمكن الاحتفاظ به.
- لا تُسمِّ mock function `sendToServer` أو `authenticateUser` بما يوحي بتنفيذ غير موجود.

## 14. الوصولية وإتاحة الاستخدام

- تنقل كامل بلوحة المفاتيح مع ترتيب focus منطقي.
- مؤشر focus-visible واضح.
- dialog يحبس التركيز عند الحاجة، يغلق بـ Escape إذا كان ذلك آمنًا، ويعيد التركيز إلى المشغل.
- labels وaccessible names للأزرار والأيقونات الوظيفية.
- تباين نصوص وحالات مناسب، وأحجام لمس مناسبة.
- لا تعتمد على hover وحده.
- استخدم `aria-live` للتنبيهات الديناميكية عند الحاجة دون إغراق قارئ الشاشة.
- دعم تكبير النص وعدم قص المحتوى.

## 15. الأداء وجودة التنفيذ الأمامي

- تجنب إعادة رسم مناطق كبيرة دون حاجة.
- قلل listeners المكررة ونظّف listeners/observers عند إغلاق الصفحة/المكون إذا كان عمرها مؤقتًا.
- تجنب تحميل صور ضخمة دون أبعاد أو استراتيجية ملائمة.
- لا تنفذ عمليات ثقيلة متزامنة في main thread إذا كان يمكن تجزئتها.
- حافظ على عدم وجود أخطاء Console أو موارد 404.
- افحص الحركة والتمرير على جهاز/عرض موبايل حقيقي أو محاكاة دقيقة.

## 16. الاختبارات المطلوبة

1. Unit: utilities, validation, formatters, state transition helpers.
2. Component: rendering, variants, interactions, accessibility.
3. Page: primary user flow, empty/error states and navigation.
4. Responsive: viewport matrix and overflow.
5. Regression: existing customer flows and legacy provider runtime.
6. Smoke: app entry points and all visible navigation targets.

الأمر الحالي للاختبارات: `npm test` (راجع `package.json`). لا تدّع وجود E2E أو visual regression suite ما لم تكن مضافة فعليًا.

## 17. Definition of Done — Frontend

لا تغلق المهمة إلا إذا:
- نُفذت المواصفة المتفق عليها دون تغيير غير مطلوب للهوية.
- جميع عناصر التحكم الظاهرة تعمل أو معطلة بوضوح وسبب.
- حالات loading/empty/error/success المناسبة موجودة.
- RTL والاستجابة tested على العروض المستهدفة.
- keyboard/focus/labels الأساسية سليمة.
- لا توجد أخطاء Console أو روابط/أصول مكسورة.
- اختبارات المشروع ذات الصلة ناجحة.
- لم تتأثر صفحات/تطبيقات أخرى تعتمد على الملفات المعدلة.
- حدثت الوثائق وخريطة الملفات وحالة التنفيذ.
- سجلت الملفات المعدلة والاختبارات والقيود المتبقية.

## 18. تعليمات العمل الجماعي مع AI

قبل التنفيذ: اقرأ هذا الملف، ثم `FRONTEND_FILE_CATALOG.md`، ثم وثيقة الصفحة/المكوّن، وافحص الكود الفعلي. لا تبدأ من وصف prompt فقط.

لكل مهمة: حدد النطاق، الملفات المسموح تعديلها، الملفات المرجعية، السلوك المتوقع، ما هو خارج النطاق، ومعايير القبول. لا يعمل مهندسان على نفس الملف في نفس الوقت دون تنسيق مالك الملف.

بعد التنفيذ: قدم ملخصًا، قائمة ملفات، سلوكًا تغير، اختبارات نفذت ونتائجها، لقطات/أوصاف viewport التي تم التحقق منها، ومخاطر/متبقيات. لا تدّع فحص شيء لم تفحصه.

## 19. فض النزاعات بين الوثائق

ترتيب الأولوية: (1) الكود الحالي المثبت، (2) هذه الوثيقة، (3) مواصفات الصفحة/المكوّن التفصيلية، (4) خريطة الملفات وحالة التنفيذ، (5) الوثائق القديمة المؤرشفة. عند تعارض الكود مع الوثيقة، لا تفترض أيهما صحيح: سجّل التعارض وحدد هل هو bug أم توثيق قديم قبل التغيير.
