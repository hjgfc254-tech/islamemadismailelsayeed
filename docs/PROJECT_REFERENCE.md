## 1. What the product is
An Arabic (RTL, Egyptian dialect) home-services marketplace. A **customer** describes a problem (electricity, plumbing,
carpentry, painting, cars, cleaning, appliances…), the platform matches an approved **provider** (technician), the
provider accepts, schedules, travels, works, sends a quote if needed and records completion; the customer confirms and
rates. The **admin center** approves providers, assigns requests, manages catalogue, prices, commissions, complaints,
site content, promo codes and employees (RBAC). After a price is agreed the customer pays **cash to the provider** after the
job (the platform's share is collected from the provider) or **online through Paymob** up front: the platform holds the
money until the customer confirms, then pays the provider's net in a weekly transfer; online jobs carry the «ضمان
هنصلحلك» voucher. The platform share is taken on the labour only. Online payment stays off until the Paymob keys are set.
The service catalogue (questions, served governorates) is edited and published from the Admin Center as one CDN file.
System map and runbooks: \docs/MAINTENANCE_GUIDE.md\.

Live project: Firebase project `hansalahlak`, Cloud Functions region `me-central1` (Node 24, 2nd gen).

## 3. Runtime architecture
* **Classic scripts, no bundler.** Each HTML loads ordered `<script>` tags; modules expose `globalThis.HS*` globals
  (e.g. `HSOrdersApi`, `HSCustomerHomePage`, `MP`, `CAT`).
* **Two backends, same domain code.** `services/api-client.js` defines routes (`client.define(method, path, {roles}, handler)`).
  * *Local demo mode* (`?backend=local` or no Firebase): handlers run in the browser on the localStorage store (MP).
  * *Firebase mode* (`HSFirebaseConfig.mode === 'firebase'`): the client calls the callable Functions **`api`** (one
    route call) and **`session`** (sync / content / registration ops). The server runs the **same** handlers
    (`functions/domain`) inside a Firestore transaction on a partially loaded database.
* **Server pipeline** (`functions/src/service.js`): verify Firebase Auth token → resolve actor (`identity.js`:
  `users/{uid}` → customer/provider, `admins/{uid}` → employee) → rate limit (`limits.js`) → idempotency →
  `plan.js` loads exactly the documents the route needs into `PartialDb` (`partial.js`) → `runtime.js` runs the
  domain handler → `PartialDb.commit` writes only changed documents → redaction per actor → audit log → change
  signals to affected users through Realtime Database `signals/{uid}` → clients re-sync.
* **Read model per actor**: `scope.js` decides what each actor receives in a sync (least privilege — see §6).
* **Admin-only server modules**: `content.js` (site content + media), `admin-extra.js` (settings, audit, departments,
  security, broadcasts), `workforce.js` (employees, RBAC).
* **Live updates**: RTDB `signals/{uid}` (private, per user) and `public/content` (site-content version, public read).
* **Push**: FCM web push, tokens in `pushTokens`, data-only messages rendered by the service worker.

## 5. Money rules
* Upfront price (if the item has a price): customer pays `customerPrice`; provider gets `providerAmount`; platform fee
  = difference. Otherwise a **quote** (labor + parts) approved by the customer, commission = rate% (provider special
  rate → category rate → default rate).
* **Free service** path records no amount and no commission (needs customer consent).
* **Discounts** (promo code, invite code, credit) are terms on the request and are computed once at completion
  (`applyDiscount` in `local-market-store.js`): paid from the platform commission and **capped at it**, so the
  provider's `net` never changes. The inviter's credit is added when the invited friend's first job completes.

## 6. Security / privacy model
* Firestore rules deny all client access; everything goes through Functions (Admin SDK). RTDB: private
  `signals/{uid}`, public read-only `public/content`.
* Customers see only their own requests, transactions (no provider amount / platform fee), addresses, favorites.
  They never see `customerReview` (provider's rating of them) or promo code lists.
* Providers see offered requests **without** phone/address/geo until they accept; chat is filtered to their own
  thread (`chat[].pid`).
* Admin access is per employee role (RBAC catalogue in `system/rbac`); every write is audited.
* No secrets in the repo; Firebase web config is public by design; VAPID public key only.

## Appendix A — Firestore / RTDB schema manifest (docs/FIREBASE_SCHEMA.md)

**Derived from the application, not invented.** The marketplace collections are exactly the entities of the app's
data layer (`services/local-market-store.js`, `MP.db()`) and keep their field names and identifiers. Documents are
written by `functions/src/store.js`.
- Every array entity is one document. The doc id is the entity's own `id`, so existing identifiers and relationships
  are preserved.
- `_k` is a server-maintained order key.
- Collections appear on their **first real write**; no placeholder documents are created.
- **Ownership** is the field the server uses to scope reads (`functions/src/scope.js`).
- Clients have **no direct access** (see `firestore.rules`); all access goes through the callable Functions.

## Envelope (every call resolves, never throws)
```
{ ok: true,  status: 200 | 201, data }
{ ok: false, status, error: { code, message, details? } }
```
| code | status | meaning |
|---|---|---|
| BAD_REQUEST | 400 | malformed request |
| UNAUTHENTICATED | 401 | no actor for a non-public route |
| FORBIDDEN | 403 | wrong role, demo RBAC denial, or non-writable field |
| NOT_FOUND | 404 | unknown route, missing record, **or a record the actor may not see** (no existence leak) |
| CONFLICT | 409 | state does not allow the action (e.g. approving a zero quote, completing a paid job on the free path) |
| VALIDATION | 422 | field errors in `details` (`{ field: message }`) |
| INTERNAL | 500 | handler threw |
| UNAVAILABLE | 503 | local store not loaded, or the remote transport failed |

`HSApiClient.viewState(result)` maps a result to the UI state every screen must render: `loading` (no result yet) ·
`ready` · `empty` · `error` · `denied` (401/403).

## Actor and permission boundary
`services/auth-api.js` derives the actor from the **existing** demo sessions, for the app that is running only:
- customer: localStorage `hs_user` → MP customer by phone (a suspended customer has no actor);
- provider: sessionStorage `hs_provider_demo_session` → MP provider with status `approved`. A pending, rejected or
  suspended registration has **no** provider role, because registering never grants it;
- admin: sessionStorage `hs_admin_demo_session` → active `HSAdminRbac` roster employee. When
  `HSAdminPermissionGuard` is loaded, admin routes also check the employee's module permission.

Each route declares its roles. The mock returns 401 when there is no actor and 403 when the role is wrong. Ownership is
checked per record: a customer only reaches their own requests, addresses and complaints; a provider only reaches
requests offered or assigned to them. **This is a demo boundary.** A real backend must enforce all of it server-side.

## Business rules at the boundary (also enforced in the store)
- **Upfront pricing (Uber model):** the admin sets a base price per service key (catalog item id or service id) = the provider amount. At booking the request gets `pricing = {base, rate, customerPrice = round(base × (1 + markupRate/100)), providerAmount, platformFee}`, which is fixed (`agreedValue = customerPrice`). Completion records `value = customerPrice`, `net = providerAmount − deductions`, `commission = platformFee`. A price adjustment after inspection is a quote whose total is the new provider amount; the customer approves `customerTotal` (same markup). Payment today: the customer pays the provider; the platform share is collected from the provider (`collection: pending`). Customers never see the provider amount, platform fee or quote breakdown of priced requests. No configured price → the previous flow (value at completion, commission rate). `markupRate` defaults to `defaultRate`.
- A quote total must be **> 0**. It is refused on submit (422) and on approve (409).
- A job done without charge uses the **free-service** routes (propose → customer accepts or declines → provider
  completes). The result has value 0, no commission, and a transaction with `free:true, collection:'none'`. Collection
  cannot be set on it.
- **Paid order lifecycle (corrected 2026-11-14):**
  ```
  received → searching → sent ─respond(accept)→ accepted ─confirmTime→ scheduled ─advance→ enroute ─advance→ arrived ─advance→ started
  started ─quotes (provider)→ quote ─quote/approve (customer)→ started [agreedValue = quote total]
                              quote ─quote/reject (customer)→ started (provider may send a new quote)
  started ─complete (provider; agreed price, or value > 0 when no quote)→ completed [finalValue, one transaction]
  completed ─close (customer confirms)→ closed ─review (customer, once)
  cancel: customer/admin before `started` · free service: started ─free→ proposed ─free/respond→ accepted ─free/complete→ completed (value 0)
  ```
  - Approving a quote **does not** complete the job.
  - Only a `pending` quote can be approved or rejected, once. An approved quote cannot be replaced or rejected.
    Sending a new quote while one is pending marks the old one `superseded`.
  - Completion is refused while a quote awaits the customer, and at any amount other than the agreed price.
  - `advance` only performs `enroute`, `arrived` and `started`; the other states go through their own validated routes.
  - Exactly one transaction is created, at completion. Tests: `tests/unit/order-lifecycle.test.js` and
    `api-adapters.test.js`.
- A provider edits only `name, phone, type, cats, govs, areas, years, bio, docs`. `status`, `specialRate` and rating are
  rejected (403).
- The public catalogue lists only approved providers and never returns `phone`, `docs`, `specialRate` or `status`.

### Data separation by role (always on)
